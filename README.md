# dv2-public-data-demo

A minimal, runnable Data Vault 2.0 reference implementation on a public Snowflake dataset. Built with **dbt + AutomateDV** on **Snowflake** to demonstrate hubs, links, satellites, hashdiffs, and a business-vault layer, the patterns enterprise data teams actually use, on data anyone can query.

> **Why this repo exists:** Data Vault 2.0 is widely used at insurance, financial, and healthcare companies, but is rarely demonstrated publicly because most production implementations live behind enterprise firewalls. This is the smallest defensible reference, designed to be read and understood in 5 minutes, not a sprawling enterprise simulation.

> **Why Snowflake:** AutomateDV (formerly dbtvault) is built primarily for Snowflake. It's the reference adapter with the most macro coverage. Most production Data Vault deployments at scale run on Snowflake. This repo runs entirely inside the **Snowflake 30-day free trial**. It uses the **Cybersyn NYC TLC** dataset from the Snowflake Marketplace (free), so reviewers can reproduce it end-to-end without paying.

---

## What it demonstrates

- **Raw vault structure**  hubs, links, and satellites built with the [`automate_dv`](https://automate-dv.com/) dbt package on Snowflake
- **Hash keys + load metadata**  every raw vault model carries `HASH_KEY`, `LOAD_DATETIME`, and `RECORD_SOURCE` columns generated by AutomateDV macros
- **Hashdiff for change detection**  satellites use a hashdiff column to identify when descriptive attributes change, enabling SCD Type 2 history without column-by-column comparison
- **Business vault layer**  derived metrics (e.g., `tip_pct`, `fare_per_mile`) computed once and reused, separating the immutable raw vault from analytical computations
- **Information mart pattern**  one flat-dimensional view that the consumption layer (Power BI, Tableau, Looker) reads from, hiding raw-vault complexity from BI users
- **dbt tests + dbt-docs**  uniqueness, not-null, and referential tests on every hub and link, plus a hosted lineage graph
- **Snowflake-native patterns**  role/database/schema separation for raw vault vs. business vault vs. information mart, virtual warehouse sizing notes, and a Time Travel demo for audit-grade lineage

## Models

### Raw vault (`models/raw_vault/`)

| Model | Type | Grain | Business key |
|---|---|---|---|
| `hub_vendor` | Hub | One row per vendor | `vendor_id` |
| `hub_pickup_zone` | Hub | One row per taxi pickup zone | `pickup_location_id` |
| `link_vendor_zone` | Link | One row per vendor × zone combination observed in trips | `vendor_id` + `pickup_location_id` |
| `sat_vendor_details` | Satellite | SCD2 history of vendor descriptive attrs | `hub_vendor.HASH_KEY` |
| `sat_zone_details` | Satellite | SCD2 history of zone descriptive attrs | `hub_pickup_zone.HASH_KEY` |

### Business vault (`models/business_vault/`)

| Model | Purpose |
|---|---|
| `bv_trip_metrics` | Per-trip derived metrics: `tip_pct`, `fare_per_mile`, `is_peak_hour`, `is_long_trip`. Computed once here, reused by every downstream consumer. |

### Information mart (`models/information_mart/`)

| Model | Purpose |
|---|---|
| `im_vendor_zone_daily` | Flat daily fact at vendor × zone grain. Joins the raw vault + business vault into a single wide table that BI tools can query without understanding hubs/links. |

## How to run it

### Option A  `dbt-core` CLI (recommended. the repo is the deliverable)

```bash
# 1. Sign up for Snowflake (30-day free trial, no credit card required for standard trial)
#    https://signup.snowflake.com/   pick AWS or Azure, any region.

# 2. In the Snowflake UI: Marketplace → search "Cybersyn NYC TLC" → "Get" (free, zero-copy mount).

# 3. Clone
git clone https://github.com/linsleymichira/dv2-public-data-demo.git
cd dv2-public-data-demo

# 4. Set up your dbt profile (Snowflake adapter)
cp profiles.yml.example ~/.dbt/profiles.yml
# Edit ~/.dbt/profiles.yml with your Snowflake account, user, role, warehouse, database, schema.

# 5. Install dbt-snowflake + AutomateDV
pip install dbt-snowflake
dbt deps                # installs automate_dv from packages.yml

# 6. Build everything
dbt build               # runs models + tests in dependency order

# 7. Browse lineage + docs locally
dbt docs generate
dbt docs serve          # opens http://localhost:8080
```

Total runtime on an `XSMALL` Snowflake warehouse: **under 3 minutes** end-to-end. Burns roughly 5–10 credits of the $400 trial allowance, or ~2% of the trial budget. Plenty of headroom to rerun.

### Option B  dbt Cloud Developer (hosted IDE, free)

The repo also runs on [dbt Cloud Developer](https://www.getdbt.com/pricing) (free, 1 user). Sign in at `cloud.getdbt.com`, link the GitHub repo, point the connection at your Snowflake trial, and `dbt build`. The screenshot in [`docs/dbt-cloud-lineage.png`](docs/dbt-cloud-lineage.png) shows the lineage graph rendered there.

## What's interesting (the stuff hiring managers ask about)

1. **Why a hashdiff instead of column-by-column comparison?**  Satellites detect change by hashing all descriptive columns into a single `HASHDIFF` and comparing only that. This makes change detection O(1) per row, regardless of how many descriptive columns the satellite carries, which is critical when satellites are 50+ columns wide.
2. **Why hash keys instead of natural keys for joins?**  Hash keys (MD5 by default in AutomateDV. SHA-256 configurable) give every entity a fixed-width primary key regardless of source-system key shape. Joins stay fast even when business keys are long strings or composite. On Snowflake, fixed-width hash keys also cluster better.
3. **Why is the link table grain "one row per combination observed" rather than "one row per trip"?**  Trip-grain belongs in a transactional satellite or fact, not in the link itself. The link captures the *relationship* between the vendor and the zone. the *transaction* is captured at the trip-level satellite. This keeps the raw vault immutable: a link row, once inserted, is never updated.
4. **Why a separate business vault?**  Raw vault is a faithful, append-only mirror of the source. The moment you start computing `tip_pct = tip/fare`, you've made an analytical decision that may need to change later. Business vault isolates those decisions, so the raw vault stays trustworthy as the audit-grade source.
5. **Where would this break at scale?**  Single-source demos hide multi-source pain. In production, hubs gather business keys from multiple sources, and the `RECORD_SOURCE` column starts earning its keep. This repo doesn't model that. please see the Roadmap.
6. **Why Snowflake (and not BigQuery / Databricks / Postgres)?**  AutomateDV is primarily built and tested for Snowflake  it's the reference adapter. Snowflake's separation of compute (warehouses) from storage maps cleanly onto the Data Vault layering: raw vault and business vault can run on differently-sized warehouses, and zero-copy clones make it cheap to spin up dev replicas of the raw vault. The same patterns *do* port to BigQuery/Databricks (AutomateDV supports both), but the macros are best-tested on Snowflake.

## Note on scope

A common Data Vault demo description reads "1 hub, 2 satellites, 1 link," but a link, by definition, connects 2+ hubs, so the smallest coherent DV2 footprint is **2 hubs + 1 link + 2 satellites + 1 business-vault model**. That's what this repo ships. The intent is the *smallest defensible reference*, not the smallest possible file count.
