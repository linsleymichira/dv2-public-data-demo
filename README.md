# dv2-public-data-demo

A minimal, runnable Data Vault 2.0 reference implementation on a public BigQuery dataset. Built with **dbt + AutomateDV** to demonstrate hubs, links, satellites, hashdiffs, and a business-vault layer, the patterns enterprise data teams actually use, on data anyone can query.

> **Why this repo exists:** Data Vault 2.0 is widely used at insurance, financial, and healthcare companies, but is rarely demonstrated publicly because most production implementations live behind enterprise firewalls, which is the smallest defensible reference, designed to be read and understood in 5 minutes, not a sprawling enterprise simulation.

---

## What it demonstrates

- **Raw vault structure**  hubs, links, and satellites built with the [`automate_dv`](https://automate-dv.com/) dbt package
- **Hash keys + load metadata**  every raw vault model carries `hash_key`, `load_datetime`, and `record_source` columns generated by AutomateDV macros
- **Hashdiff for change detection**  satellites use a hashdiff column to identify when descriptive attributes change, enabling SCD Type 2 history without column-by-column comparison
- **Business vault layer**  derived metrics (e.g., `tip_pct`, `fare_per_mile`) computed once and reused, separating the immutable raw vault from analytical computations
- **Information mart pattern**  one flat-dimensional view that the consumption layer (Looker, Power BI, Tableau) reads from, hiding raw-vault complexity from BI users
- **dbt tests + dbt-docs**  uniqueness, not-null, and referential tests on every hub and link, plus a hosted lineage graph

## Architecture

```
bigquery-public-data.new_york_taxi_trips
            │
            ▼
        staging (1:1 source view, light renaming)
            │
   ┌────────┼────────┐
   ▼        ▼        ▼
 hubs     links    satellites          ← raw vault (immutable, append-only)
   │        │        │
   └────────┼────────┘
            ▼
    Business Vault                     ← derived metrics
            │
            ▼
    information mart                   ← what Looker / Power BI reads
```

## Stack

- **Warehouse:** Google BigQuery (free public dataset, free-tier query budget covers the demo)
- **Transformation:** [dbt-core](https://github.com/dbt-labs/dbt-core) 1.7+
- **Data Vault macros:** [`automate_dv`](https://automate-dv.com/) (formerly `dbtvault`) 0.10+
- **Tests:** dbt built-ins + a hashdiff-uniqueness check
- **Docs:** `dbt docs generate` → hosted on GitHub Pages

## Models

### Raw vault (`models/raw_vault/`)

| Model | Type | Grain | Business key |
|---|---|---|---|
| `hub_vendor` | Hub | One row per vendor | `vendor_id` |
| `hub_pickup_zone` | Hub | One row per taxi pickup zone | `pickup_location_id` |
| `link_vendor_zone` | Link | One row per vendor × zone combination observed in trips | `vendor_id` + `pickup_location_id` |
| `sat_vendor_details` | Satellite | SCD2 history of vendor descriptive attrs | `hub_vendor.hash_key` |
| `sat_zone_details` | Satellite | SCD2 history of zone descriptive attrs | `hub_pickup_zone.hash_key` |

### Business vault (`models/business_vault/`)

| Model | Purpose |
|---|---|
| `bv_trip_metrics` | Per-trip derived metrics: `tip_pct`, `fare_per_mile`, `is_peak_hour`, `is_long_trip`. Computed once here, reused by every downstream consumer. |

### Information mart (`models/information_mart/`)

| Model | Purpose |
|---|---|
| `im_vendor_zone_daily` | Flat daily fact at vendor × zone grain. Joins the raw vault + business vault into a single wide table that BI tools can query without understanding hubs/links. |

## How to run it

```bash
# 1. Clone
git clone https://github.com/linsleymichira/dv2-public-data-demo.git
cd dv2-public-data-demo

# 2. Set up your dbt profile (BigQuery, OAuth, or service account)
cp profiles.yml.example ~/.dbt/profiles.yml
# Edit ~/.dbt/profiles.yml with your GCP project + dataset

# 3. Install the AutomateDV package
dbt deps

# 4. Build everything
dbt build              # runs models + tests in dependency order

# 5. Browse lineage + docs locally
dbt docs generate
dbt docs serve         # opens http://localhost:8080
```

Total runtime on a free-tier BigQuery project: **under 2 minutes**, well under 1 GB of query bytes.

## What's interesting (the stuff hiring managers ask about)

1. **Why a hashdiff instead of column-by-column comparison?**  Satellites detect change by hashing all descriptive columns into a single `hashdiff` and comparing only that, which makes change detection O(1) per row, regardless of how many descriptive columns the satellite carries  critical when satellites are 50+ columns wide.
2. **Why hash keys instead of natural keys for joins?**  Hash keys (SHA-256 of the business key, by default) give every entity a fixed-width primary key regardless of source-system key shape. Joins stay fast even when business keys are long strings or composite.
3. **Why is the link table grain "one row per combination observed" rather than "one row per trip"?**  Trip-grain belongs in a transactional satellite or fact, not in the link itself. The link captures the *relationship* between vendor and zone; the *transaction* is captured in the trip-level satellite, which keeps the raw vault immutable: a link row, once inserted, is never updated.
4. **Why a separate business vault?**  Raw vault is a faithful, append-only mirror of the source. The moment you start computing `tip_pct = tip/fare`, you've made an analytical decision that may need to change later. Business vault isolates those decisions, so the raw vault stays trustworthy as the audit-grade source.
5. **Where would this break at scale?**  Single-source demos hide multi-source pain. In production, hubs gather business keys from multiple sources, and the `record_source` column starts earning its keep, which repo doesn't model that  see Roadmap.

## Note on scope

A common Data Vault demo description reads "1 hub, 2 satellites, 1 link,"  but by definition, a link connects 2+ hubs, so the smallest coherent DV2 footprint is **2 hubs + 1 link + 2 satellites + 1 business-vault model**. That's what this repo ships. The intent is the *smallest defensible reference*, not the smallest possible file count.
